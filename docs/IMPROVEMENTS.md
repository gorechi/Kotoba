## 1. Надёжность данных (P0)

### 1.1. Строгая проверка импорта и страховочная копия `[x]`

**Проблема.** `normalizeData()` всегда добавляет встроенные колоды и карточки и не отвергает мусор. `BackupPanel` использует его для предпросмотра. Если выбрать произвольный JSON, предпросмотр покажет правдоподобные числа, а после подтверждения данные заменятся стартовым набором.

**Что сделать:**

- отдельный валидатор резервной копии: объект, массивы `decks`/`cards`, хотя бы одна валидная колода, поддержка `version: 1/2` и легаси-файлов без версии;
- предпросмотр с реальными количествами из файла и числом пропущенных повреждённых записей;
- отказ от импорта с понятным сообщением, если файл не похож на копию Котобы;
- автоматическая страховочная копия текущих данных в `%APPDATA%\Kotoba\backups\` перед импортом;
- если страховочную копию создать не удалось — импорт отменяется;
- два режима: **«Заменить всё»** и **«Добавить колоды»** (без дублирования встроенных колод);
- отмена импорта в текущей сессии;
- строки RU/EN.

**Критерии готовности:**

- случайный JSON (`{ "hello": "world" }`) не открывает подтверждение импорта;
- валидная копия показывает настоящие количества колод и карточек;
- перед импортом появляется файл `backups/kotoba-before-import-*.json`;
- режим «Добавить колоды» сохраняет текущие данные и добавляет только свои колоды из копии;
- после импорта можно нажать «Отменить импорт» и вернуть прежние данные;
- `npm run build` проходит, ошибок в консоли нет.

**Файлы:** `src/lib/backup.ts`, `src/lib/normalize.ts`, `src/components/BackupPanel.tsx`, `electron/backup.cjs`, `electron/main.cjs`, `electron/preload.cjs`, `src/types.ts`, `src/locales/ru.ts`, `src/locales/en.ts`, `src/styles.css`.

**Реализовано в ветке `feature/data-reliability`:**

- `inspectBackup()` проверяет форму файла и не подмешивает seed-данные;
- предпросмотр показывает валидные колоды/карточки и пропущенные записи;
- невалидный JSON отклоняется до открытия подтверждения;
- Electron создаёт `backups/kotoba-before-import-*.json`; при ошибке импорт отменяется;
- режимы «Заменить всё» и «Добавить колоды»;

### 1.2. Восстановление после повреждённого файла `[x]`

Если `kotoba-content.json` не парсится, `readParts()` возвращает `null`, `normalizeData(null)` создаёт seed-данные, а `dirtyRef` стартует как `ALL_DIRTY` — первый автосейв перезаписывает content, settings, progress и history. Нужно отличать отсутствие файла от повреждения, хранить `.bak`, не сохранять автоматически после ошибки и показывать экран восстановления/импорта.

**Что сделано:**

- файловая логика вынесена в `electron/storage.cjs` и покрыта сценарной проверкой;
- при записи предыдущая версия каждого файла сохраняется в `.bak`;
- повреждённый файл переименовывается в `*.corrupt-<дата>` и не затирается;
- при наличии `.bak` данные восстанавливаются автоматически, основной файл возвращается на место, в приложении появляется уведомление «Часть данных восстановлена…»;
- если восстановиться не удалось, приложение показывает экран восстановления и **не сохраняет** ничего до выбора действия;
- на экране можно импортировать резервную копию, попробовать снова, открыть папку с данными или начать с пустого профиля;
- состояние блокировки хранится в `kotoba-recovery.json` и переживает перезапуск;
- повреждённые настройки не блокируют приложение: используются значения по умолчанию, показывается предупреждение;
- потерянный `kotoba-content.json` при наличии прогресса/истории/настроек тоже приводит к экрану восстановления, а не к тихому seed.

**Критерии готовности:**

- битый content без `.bak` → экран восстановления, новые данные не пишутся;
- битый content с `.bak` → приложение запускается, данные восстановлены, показан баннер;
- битый progress с `.bak` → прогресс восстановлен;
- битый settings → приложение работает на значениях по умолчанию и предупреждает;
- после закрытия на экране восстановления и повторного запуска экран остаётся;
- импорт копии и «начать с нуля» возвращают приложение к работе;
- `npm run build` проходит, ошибок в консоли нет.

**Файлы:** `electron/storage.cjs`, `electron/main.cjs`, `src/lib/storage.ts`, `src/state/store.tsx`, `src/components/RecoveryScreen.tsx`, `src/App.tsx`, `src/components/Icon.tsx`, `src/locales/ru.ts`, `src/locales/en.ts`, `src/styles.css`.

### 1.3. Видимый статус сохранения `[x]`

`persistDirty()` проглатывает ошибку и помечает данные dirty для повтора, но пользователь ничего не видит. В синхронном сохранении при закрытии ошибка тоже глотается и возвращается `true`. Нужен индикатор «Сохранено / Не удалось сохранить», повтор и корректная обработка sync-ошибки.

**Что сделано:**

- в сторе появилось состояние `saveState`: `idle / saving / saved / error`;
- в заголовке окна показывается «Сохранение…» и «Сохранено» (последнее скрывается через ~2 секунды);
- при ошибке в заголовке появляется красный статус «Не сохранено» с кнопкой «Повторить»;
- дополнительно показывается баннер с объяснением и кнопкой повтора; он виден и в режиме «Дзен»;
- `flush()` теперь возвращает `boolean`, ждёт текущую запись и повторяет, пока не сохранит все накопленные изменения;
- кнопка закрытия окна не закрывает приложение, если сохранить не удалось;
- `savePartsSync` возвращает реальный результат записи, а не всегда `true`;
- `saveStorageSync()` и `flushSync()` возвращают `boolean`, ошибка синхронной записи больше не теряется;
- ошибки пишутся в консоль с префиксом `[kotoba] save failed` для диагностики.

**Критерии готовности:**

- при обычном изменении видны статусы «Сохранение…» → «Сохранено»;
- при ошибке видны «Не сохранено» и баннер с повтором;
- повтор при продолжающейся ошибке оставляет статус ошибки;
- после успешного повтора баннер исчезает, статус становится «Сохранено»;
- закрытие окна при ошибке сохранения не происходит;
- закрытие после успешного сохранения происходит;
- `npm run build` проходит.

**Файлы:** `src/state/store.tsx`, `src/components/TitleBar.tsx`, `src/App.tsx`, `src/lib/storage.ts`, `src/types.ts`, `electron/main.cjs`, `src/locales/ru.ts`, `src/locales/en.ts`, `src/styles.css`.

### 1.4. Защита от второго экземпляра `[x]`

Два окна могут писать в одни и те же JSON-файлы, и последнее сохранение затрёт первое. Добавить `app.requestSingleInstanceLock()` и фокус уже открытого окна.

**Что сделано:**

- при старте вызывается `app.requestSingleInstanceLock()`;
- если лок не получен, второй экземпляр завершается через `app.quit()` до создания окна и загрузки данных;
- на `second-instance` первый экземпляр:
  - восстанавливает окно из минимизированного состояния;
  - показывает его, если оно было скрыто;
  - вызывает `app.focus({ steal: true })` для Windows и `mainWindow.focus()`;
- добавлены флаги `windowReady` и `pendingFocus`: повторный запуск во время старта не теряется, а фокус применяется после `ready-to-show`;
- если окна ещё нет или оно уже закрывается, фокус запоминается и применяется к следующему созданному окну;
- разные `--user-data-dir` по-прежнему могут работать параллельно, потому что это разные наборы данных;
- один и тот же профиль всегда имеет только одного писателя.

**Критерии готовности:**

- повторный запуск завершается за доли секунды с кодом 0;
- первый экземпляр остаётся жив, второе окно не создаётся;
- файлы данных не меняются от запуска второго экземпляра;
- после сворачивания повторный запуск возвращает окно и фокусирует его;
- два экземпляра с разными `--user-data-dir` работают независимо;
- `npm run build` и `npm run dist` проходят.

**Файлы:** `electron/main.cjs`.

### 1.6. Точечная запись прогресса `[x]`

Сейчас при каждом ответе перезаписывается весь progress-map, а оценка «Снова» ещё и весь content из-за `lastMistakeAt` на карточке. Перенести `lastMistakeAt` в progress, добавить батчинг/троттлинг и запись на выходе из сессии.

**Что сделано:**

- `lastMistakeAt` перенесён из `Card` в `SrsState`, то есть в progress-часть;
- старые данные мигрируют при загрузке: если `lastMistakeAt` ещё лежит в контенте карточки, он переносится в `srs.lastMistakeAt`;
- оценка «Снова» больше не помечает content грязным — перезаписываются только progress и history;
- ответы собираются в пачку:
  - запись выполняется через 5 секунд после последнего ответа;
  - при непрерывной учёбе прогресс пишется не реже чем раз в 10 секунд;
  - ручная отмена оценки и другие изменения прогресса участвуют в том же батче;
- при выходе из подхода вызывается `flush()` — накопленная пачка сразу пишется на диск;
- при закрытии приложения синхронный flush по-прежнему записывает всё;
- редактирование карточек, сброс прогресса и другие изменения контента пишутся сразу, как раньше;
- «ошибки за неделю» и сортировка ошибок используют `srs.lastMistakeAt`;
- сброс/отметка «знаю» очищают `lastMistakeAt` вместе с SRS;
- бэкапы и `readAppData` автоматически получают `lastMistakeAt` из progress.

**Критерии готовности:**

- старый `lastMistakeAt` из контента переносится в progress;
- после миграции в `kotoba-content.json` больше нет `lastMistakeAt`;
- оценка «Снова» не перезаписывает content;
- несколько ответов подряд не пишут progress на каждый ответ;
- при паузе прогресс записывается;
- при непрерывной учёбе прогресс пишется не реже раза в 10 секунд;
- выход из подхода сразу сохраняет оставшуюся пачку;
- «ошибки за неделю» работают;
- `npm run build` и `npm run dist` проходят.

**Файлы:** `src/types.ts`, `src/lib/normalize.ts`, `src/lib/custom-study.ts`, `src/pages/CardBrowser.tsx`, `src/state/store.tsx`, `src/App.tsx`.

## 3. Производительность и структура (P2)

### 3.1. Локали и контентные переводы `[ ]`

`i18n.ts` грузит оба языка сразу (`import.meta.glob(..., { eager: true })`), а в локалях лежат ещё и переводы кандзи (ru — ~112 КБ, en — ~86 КБ). Разделить UI-строки и контентные переводы, неактивный язык подгружать лениво.

### 3.2. Ленивые маршруты `[ ]`

Один JS-чанк ~677 КБ, Vite уже предупреждает. Ленивые `CardBrowser`, `Stats`, `Decks`, Help и данные кандзи.

### 3.3. Сабсет шрифта `[ ]`

Klee One занимает 8,7 МБ. Сабсеттинг по кане, N5/N4 и пунктуации уменьшит размер и память.

### 3.4. CSS и крупные компоненты `[ ]`

`styles.css` — ~7 000 строк. Разбить по фичам. `CardBrowser`, `Session`, `Decks` — вынести хуки и подкомпоненты.

### 3.5. Точечные обновления `[ ]`

`structuredClone` на каждое редактирование и полные перезаписи массивов. Перейти на targeted immutable-обновления, как уже сделано в `rateCard`.

### 3.6. Кэш проверки обновлений `[ ]`

Проверять не чаще раза в сутки и запоминать результат, чтобы не дёргать GitHub при каждом запуске.
