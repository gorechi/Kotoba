# Правила работы над Котобой

Короткий свод договорённостей. Нужен, чтобы не терять контекст между сессиями и не плодить ветки.

## Размер фичи

Перед началом разработки фиксируем размер. Если пользователь его не назвал — **спросить до начала работы**, не оценивать молча.

- **Большая** — новая подсистема, миграция данных, новая платформа, недели работы.
- **Средняя** — несколько дней, несколько экранов или заметная переделка данных.
- **Мелкая** — до дня, один экран или одна небольшая функция.

Оценка совместная. При сомнении считаем по верхней границе.

## Ёмкость ветки

Бюджет одной ветки — **6 очков**:

- большая — 6;
- средняя — 3;
- мелкая — 2.

Отсюда допустимые наборы:

- 1 большая;
- 2 средние;
- 3 мелкие;
- 1 средняя + 1 мелкая.

Больше — нельзя. Если фича не влезает в остаток бюджета, она ждёт следующей ветки.

**Не расходуют бюджет:**

- исправления по текущей ветке, найденные при тестировании;
- тесты, документация и рефакторинг внутри текущей фичи;
- правки текстов и мелкая полировка уже сделанного.

Если фича оказалась больше, чем оценивали: остановиться, переоценить и решить — дробить или выносить остаток в следующую ветку.

## Ветки

1. Ветка создаётся от актуального `main`.
2. Ветки не стекуются. В любой момент открыта одна ветка.
3. Ветка наполнилась — новые фичи не начинаем, пока текущую не протестировали и не слили.
4. Тестирует пользователь. Найденные баги правим в этой же ветке.
5. Ветка считается готовой после явного «работает» от пользователя.
6. После этого — merge в `main`, ветку удалить. Следующая ветка — только после merge.
7. Если ветка реализует фичу из `docs/BACKLOG.md`, при слиянии в `main` эта фича удаляется из бэклога. Бэклог содержит только несделанное.
8. Слияние и пуш в `main` — после явного подтверждения пользователя.

## Тесты

- Каждая новая фича покрывается автотестами.
- Ветка не сливается в `main`, пока `npm run check` не проходит.
- Если для покрытия нужна новая инфраструктура (jsdom, `fake-indexeddb`), она входит в работу по фиче.
- Стратегия и текущее покрытие — `docs/TESTING.md`.

## Ревью кода

«Провести ревью кода» — это не чтение диффа и не только запуск тестов. Нужно провести полную инвентаризацию кода, убрать лишнее и привести проект в порядок.

Процесс:

1. **Ветка.** Начать с чистого `main`, создать отдельную ветку `refactor/...` или `chore/...`. Не начинать на грязном рабочем дереве. Чужие папки вроде `kana-*` не трогать и не коммитить.
2. **Базовая линия.** До изменений прогнать `npm run check`, чтобы знать исходное состояние.
3. **Аудит.** Проверить весь проект, а не только недавние файлы:
   - неиспользуемые экспорты, функции, константы, типы и целые файлы;
   - неиспользуемые зависимости и ассеты;
   - неиспользуемые CSS-классы, `@keyframes` и переменные;
   - неиспользуемые ключи локалей;
   - мёртвые пропсы, ветки компонентов и устаревшие стили после переделок;
   - дублирование и места, где нужен небольшой рефакторинг.
4. **Динамика.** Не удалять код только по одному совпадению в поиске. Учитывать:
   - классы, собранные через шаблонные строки (`save-status--${...}`, `heatmap-level-*`);
   - ключи локалей с плюральными формами и динамическими префиксами;
   - ленивые импорты и пути, собранные из строк;
   - тестовые фикстуры и утилиты, которые используются только тестами.
5. **Чистка.** Удалять только подтверждённо мёртвое. Символы, которые используются только внутри своего файла, лишать лишнего `export`. Не менять поведение без необходимости. Ассеты с исходной или лицензионной ценностью (например, полный TTF при использовании subset-версии) оставлять и отдельно отмечать в отчёте.
6. **Проверка.** После крупных блоков правок запускать `npm run typecheck` или `npm run check`. Финальный `npm run check` обязателен. Если менялись UI, CSS или локали — дополнительно `npm run build` и браузерный смоук основных экранов.
7. **Отчёт.** Перечислить, что найдено, что удалено, что оставлено осознанно, сколько тестов прошло, какие команды запускались и какие остались риски. Ветку не сливать в `main` без явного «работает» от пользователя.

Критерий завершения: ветка создана от чистого `main`, лишнее убрано или обоснованно оставлено, рабочее дерево не содержит чужих файлов, финальный `npm run check` проходит, отчёт готов.

## Релизы

- Версия поднимается при выпуске, а не на каждую фичу.
- Установщик собирается только по просьбе пользователя.
- Тестовые установщики называются с суффиксом, чтобы не путать с выпущенными.

## Бэклог и данные

- `docs/BACKLOG.md` — источник истины по приоритетам и причинам отказов.
- Новые идеи и решения сразу фиксируются в бэклоге.
- Не коммитить чужие рабочие папки (`kana-*` и подобные).
- Данные пользователя важнее удобства: миграции, импорт и резервные копии должны быть безопасными.

## Принципы продукта

- Без геймификации, напоминаний и давления на пользователя.
- Без настроек, которые ломают дизайн.
- Без контента и данных с неясной лицензией.
- Фичи ради фич не добавляем.
